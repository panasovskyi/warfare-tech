# Warfare Tech — інструкції для Claude

Warfare Tech — англомовний новинний сайт про військові технології (мілтек). Назва — як у репозиторію `panasovskyi/warfare-tech` (скоріш за все остаточна); "SITREP" — стара заглушка, так досі називається локальна тека `d:\sitrep` і макет. Власник проєкту вчиться: після Express освоїв NestJS на цьому бекенді, далі — фронт на Next.js.

## Як працювати

- **Не писати код і не створювати/редагувати файли, поки власник прямо не попросить.** Діє для всього репозиторію (server, client, ingestion). Власник тренується і пише код сам.
- **Пояснювати прозою.** Назви класів, декораторів, методів — так, блоки коду — лише коли прямо попросять ("напиши код", "покажи код"). Навіть ілюстративні приклади в поясненнях — це "написання коду".
- **Коли просять код — давати його текстом у чаті**, а не створювати файли, якщо не сказано інакше ("сам виправ", "створи файл", "додай", "зроби", "дороби", "пропиши", "перенеси", "постав туду").
- **Shell-команди (npm, npx, prisma, git) — давати текстом**, власник запускає їх сам.
- **Можна без дозволу:** читати й переглядати файли, запускати перевірки лише для читання (`npx tsc --noEmit`, `npx eslint`, `npx prettier --check`, GET-запити curl до локальних серверів).
- **Питати перед діями, що змінюють дані:** запити, які пишуть у базу, `prisma migrate`, `git`-операції.
- **Не запускати `prettier --write` на файлах, які власник може редагувати** — це вже раз зіпсувало незбережений буфер у VS Code. Форматувати лише файли, які щойно написав сам; решту — власник через `npm run format`.
- **Не згадувати зауваження лінтера й форматування** (попередження ESLint, лапки, крапки з комою, відступи, "запусти format") у розборах, якщо проблема не критична — не ламає збірку і не ховає справжній баг.
- **Aria і семантику (рівні заголовків `h1`–`h6`, `aria-label`, `aria-current`, `nav`/`section`) розв'язуємо наприкінці, коли вся сторінка готова.** Рівні заголовків відносні: якщо між `h2` і `h3` з'явиться ще один блок, усе після нього треба зсувати на +1, тож ранні виправлення — зайва робота. У процесі це не виправляємо і не згадуємо в розборах; де воно важливе — лишаємо на місці `TODO (семантика): …` (за цією позначкою наприкінці все знаходиться пошуком, тоді проходимо сторінку зверху вниз).
- **Розбір коду — пронумерованими пунктами**, щоб власник відповідав по номерах: "1–3 роби", "4 туду". "Туду" = TODO-коментар у коді на тому місці, українською. Виконані TODO прибирати. **Відкладені завдання — не туду:** вони живуть у `BACKLOG.md` (корінь репозиторію). Коли власник просить знайти туду, шукати лише `TODO` у коді й не переказувати беклог; беклог читати й показувати лише коли просять саме беклог. Те, що власник закрив (не робимо), не писати ні в коді, ні в беклозі.
- **Не забігати наперед.** Відповідати рівно на поточний крок; наступні кроки — коротким переліком, без реалізації.
- **Виправляти фактичні помилки** в поясненнях власника і казати про це прямо.
- **Спілкування — українською.** Код, UI і контент сайту — англійською. Коментарі в коді — як у сусідньому коді (TODO — українською).
- **Порівняння** — лише коли корисно. На бекенді основою було Express → Nest. На фронті бази порівняння немає (зрідка Vite).

## Структура репозиторію

```
/            README.md, CLAUDE.md, .vscode/settings.json
/server      NestJS API (свій README)
/client      Next.js 16
/ingestion   рерайт новин за посиланням: чернетки в Markdown, публікація з файлу (розділ Ingestion нижче, команди — ingestion/STEPS.md)
```

`.vscode/settings.json`: `eslint.workingDirectories: ["./client", "./server"]` — ESLint 9 шукає конфіг від робочої теки, без цього розширення VS Code не лінтить монорепо.

## Backend (`server/`)

**Стек:** NestJS 11, Prisma **7** + PostgreSQL + `@prisma/adapter-pg`, Zod 4, `@nestjs/jwt`, bcrypt.

**Граблі, на які вже наступали:**
- Prisma **зафіксована на v7**. `prisma@latest` тягне v8 (Platform CLI), і на ньому npm падає з помилкою `edgesOut`.
- Конфіг Prisma — `prisma7.config.ts`. Там же `migrations.seed`: ключ `"prisma"` у `package.json` Prisma 7 ігнорує.
- `migrate dev` **не запускає** `generate` — після міграції окремо `npm run prisma:generate`, потім перезапуск `start:dev`.
- Згенерований клієнт — `server/generated/prisma`, імпорт `generated/prisma/client` (через `baseUrl`), не `@prisma/client`.
- Сід (`prisma/seed.ts`) запускається через `tsx`: `ts-node` не вміє резолвити `.js`-імпорти згенерованого клієнта.
- Коли поведінка сервера не відповідає коду — перевірити, чи не висить старий процес на порту, і шукати в логах старту `Mapped {...}`.

**Середовище:** API на `http://localhost:5000/api` (глобальний префікс `api`), фронт — `http://localhost:3000` (`CLIENT_URL`, CORS увімкнено). Змінні `.env` (зразок — `server/.env.example`, такі самі зразки є в `client/` і `ingestion/`): `PORT`, `NODE_ENV`, `CLIENT_URL`, `DATABASE_URL`, `JWT_ACCESS_SECRET`, `ADMIN_EMAIL`, `ADMIN_PASSWORD` (`JWT_REFRESH_SECRET` у коді не використовується: refresh-токена нема). Збірка сервера кладе точку входу в `dist/src/main.js` (разом компілюються `prisma7.config.ts`, `generated/` і `prisma/`), тому `start:prod` — `node dist/src/main`; `generated/prisma` у git нема, на збірці потрібен `prisma generate`; `dotenv` (його імпортує `main.ts`) у `package.json` не вказаний явно, а приходить транзитивно з `prisma` (devDependency): для продакшн-встановлення без devDependencies його треба додати в `dependencies`.

**Конвенції:**
- Помилки: `ApiError extends HttpException`, тіло `{ message, fieldErrors, formErrors }` — під react-hook-form. Глобальний `ExceptionsFilter` віддає будь-який `HttpException` з його статусом (неіснуючий роут — 404, зламаний JSON — 400), помилки Prisma — через `handlePrismaError`, решта — 500 з логом. Вбудовані винятки Nest мають тіло `{ message, error, statusCode }` без `fieldErrors`/`formErrors`: клієнт (`lib/api`) і ingestion це терплять, бо ці поля в них необов'язкові.
- Валідація: `ZodValidationPipe` на `@Body` / `@Query` / `@Param`. `z.infer` — тип результату після `.transform()`. Для булевих у query — `z.stringbool()`, не `z.coerce.boolean()`. Кілька помилок на різних полях — `superRefine`, не `refine`.
- Сервіси пошуку повертають `null`, а що робити з "не знайдено", вирішує той, хто викликає (контролер кидає `ApiError.notFound`).
- Цілісність даних User (унікальність, хешування пароля) — в `UserService.create`.
- Форма результату запиту: константа в `*.queries.ts` з `satisfies Prisma.<Model>DefaultArgs`, розгортається в запиті, тип — через `Prisma.<Model>GetPayload` у `*.types.ts`. Деталі — `server/PRISMA_TYPES.md`.
- Публічні дані юзера — лише через `select` (білий список). Ніколи `include: { author: true }`: це віддає хеш пароля.
- Авторизація: `JwtGuard` + `@CurrentUser()`, ролі — `RolesGuard` + `@Roles([...])`, `@UseGuards(JwtGuard, RolesGuard)`. `POST /auth/register` — лише ADMIN: форми реєстрації й акаунтів читачів на сайті поки немає, перший адмін береться із сіду. Невірний логін чи пароль — 401 (`ApiError.unauthorized`): `formErrors` порожній, відповідь несе лише `message`, тож форма входу має показувати його, а клієнтська логіка «401 → refresh» має виключати сам запит логіну.
- Публічні запити статей фільтрують `status: PUBLISHED`.
- Схеми **пошуку** не мають бути суворішими за правила **створення** (старі дані мають лишатися досяжними).
- **Правило статті** (`create-article.schema.ts`): NEWS — рівно одне з двох: або `isWarInUkraine`, або `subcategory`. LONGREAD — ні підкатегорії, ні `isWarInUkraine`. Правило живе лише в zod (база його не гарантує); для майбутнього PATCH перевіряти злиту зі збереженою статтю.
- Назви типу статті: поле `type`, enum `ArticleType` (NEWS / LONGREAD), enum підкатегорії `ArticleSubcategory` (раніше `category`, `ArticleCategory`, `Subcategory`). Міграція `rename_category_to_type` перейменувала колонку й enum-типи в базі без втрати даних: SQL писали вручну (`ALTER TYPE … RENAME TO`, `RENAME COLUMN`), бо Prisma бачить перейменування як видалення й створення колонки і на непорожній таблиці впала б. Параметр запиту й поле JSON — `type`; старий `?category=` не дає помилки (zod відкидає невідомі ключі), а просто не фільтрує. Чернетки ingestion пишуть `type:`; дві старі чернетки в `ingestion/drafts/` ще мають `category:` (вони вже опубліковані й лише читаються для перевірки дублів за `sourceLink`).
- Slug генерується з заголовка + 6-символьний hex-суфікс — не збігається з назвами статичних сторінок фронта.
- `status` у базі за замовчуванням `PUBLISHED`: чернеток у базі не використовуємо (власник перевіряє чернетку у файлі ingestion, який сам шле `PUBLISHED`). Тож `POST /articles` без `status` публікує статтю одразу; якщо чернетки з'являться в базі — змінити default у `schema.prisma`.
- `sourceLink` не унікальний свідомо: з одного джерела (лонгрід) може вийти кілька новин. Дублі ловить ingestion, обхід — `--force` (і в `npm start`, і в `publish-draft`); унікального індексу не додавати.
- `readingTime` (хвилини читання, `Int`) рахує сервер у `getReadingTime` (`article.service.ts`: 250 слів за хвилину, округлення вгору) при створенні статті; у `createArticleSchema` поля немає, клієнт його не надсилає. Міграція `article_reading_time` порахувала наявні статті тим самим правилом у SQL — змінюєш одне, змінюй друге. Поле приходить і в списку (скалярне, `omit` прибирає лише `body`), і в деталях.
- URL у статті (`create-article.schema.ts`): `sourceLink` — лише http(s) (посилання зі сторонніх сторінок, фронт ставить їх у `href`, тож `javascript:` не можна); `mainPicture` — лише https і хост із `IMAGE_HOSTNAME` (зараз `placehold.co` і `res.cloudinary.com`), який тримаємо в синхроні з `images.remotePatterns` у `client/next.config.ts` і з дзеркалом схеми в `ingestion/src/article/article.schema.ts`: `next/image` на невідомому хості кидає помилку, і вся сторінка списку віддає 500 (так було з `example.com`). Новий хост фото = змінити всі три місця.
- `body` — Markdown, але лише те, що вміє фронт (`checkBodyMarkdown` у `create-article.schema.ts`, дзеркало — `ingestion/src/article/body-rules.ts`: тримати однаковими): абзаци, посилання лише http(s), картинки окремим абзацом з описом і підписом із дозволеного хоста (до 10), HTML заборонений. Деталі — у розділі Ingestion.

**Документація бекенду** (`server/`): `SHORT_NEST_FLOW.md`, `ALGORITHM_STEPS.md`, `STEPS_LOGIC.md`, `PRISMA_TYPES.md`. Покрокові конспекти були потрібні для вивчення Nest; для фронта — лише на прохання (є `client/API_CLIENT.md` про обгортку над fetch).

**Нотатки по бекенду (довідка):** токен доступу живе 30 днів (`auth.module.ts`) свідомо: адмін один, відкритої реєстрації нема, refresh-токен не потрібен (рішення власника). e2e-тестів нема свідомо: коли знадобляться, їх пишуть замість шаблонного `app.e2e-spec.ts`. Ендпоінтів редагування (PATCH) і видалення (DELETE) статті нема й поки не планується — правки опублікованого лише через Prisma Studio; перевірка правила статті над злитою статтею — у `BACKLOG.md` (С4). Якщо PATCH колись знадобиться: вирішити, чи можна міняти `type` і `status`; дозволити `null` для nullable-полів (`subcategory`, `photoCredit`, `source`, `sourceLink`), інакше їх не очистити; правило статті й пару `source`/`sourceLink` перевіряти над статтею, злитою зі збереженою; `createArticleSchema.partial()` не працює (Zod 4 не дозволяє `.partial()` на схемі з `superRefine`), тож поля спершу виносяться в базовий об'єкт без перевірок. `photoCredit` (автор головного фото, `String?`, до 200 символів, у схемі й міграції `article_photo_credit`) готовий на сервері, в ingestion і на сторінці статті (`figcaption` «Photo: …» на фото); автора фото в тілі статті несе підпис самої картинки. `photoAlt` (опис головного фото для скрінрідерів і соцмереж, `String?`, до 200 символів, у схемі й міграції `article_photo_alt`) необов'язковий: порожнє означає декоративне фото; у відповідях API приходить у списку й деталях.

## Ingestion (`ingestion/`)

Окремий Node-проєкт (TypeScript, `tsx`, ESM): бере статтю з дозволеного сайту, Claude переписує її англійською, результат лягає в Markdown-чернетку, власник правит її у VS Code, а команда публікації відправляє відредагований файл на сервер. Окремого інтерфейсу для перевірки немає і не планується: чернетка — це і є інтерфейс. Покрокова шпаргалка з командами — `ingestion/STEPS.md` (тримати в синхроні при зміні прапорців); сухий чекліст публікації — `ingestion/CHECKLIST.md` (теж тримати в синхроні).

**Стек:** `@anthropic-ai/sdk` (Claude Sonnet 5.5, `claude-sonnet-5-5`; id моделі лише в `src/config/config.ts`), Zod 4, `@mozilla/readability` + `jsdom`, `cloudinary`, `axios`, `yaml`, `slugify`. Усі виклики моделі — через `src/llm/llm.client.ts` (`generate`, `generateJson`).

**Команди** (з теки `ingestion`; `--` після `start` обов'язковий, інакше npm забирає прапорці собі): `npm start -- <адреса> [YYYY-MM-DD] [--image=<адреса фото>|page] [--credit="автор фото"] [--force]` (або з файлом тексту другим аргументом) — створити чернетку; `npm run publish-draft -- <файл> [--dry-run] [--force]`; `npm run attach-image` (без аргументів — найновіша чернетка + найновіше фото з теки `ingestion/photos/`, після успіху фото переїжджає в `photos/used/`; або `-- [<чернетка.md>] [<файл фото | адреса фото | page>]`); `npm run translate [-- <чернетка.md | чернетка.uk.md>]` (без шляху — найновіша чернетка; `.uk.md` перекладається цілком у англійську чернетку, `.md` з кирилицею — лише частини з кирилицею); `npm run upload-image -- <адреса | файл> --alt="…" --caption="…"` (друкує рядок картинки для вставки в текст); `npm run upload-fallback`.

**Змінні `ingestion/.env`:** `ANTHROPIC_API_KEY`, `CLOUDINARY_CLOUD_NAME` / `CLOUDINARY_API_KEY` / `CLOUDINARY_API_SECRET`, `API_BASE_URL` (разом із `/api`), `ADMIN_LOGIN` (пошта чи логін адміна), `ADMIN_PASSWORD`. Cloudinary і публікація перевіряють свої змінні лише коли потрібні.

**Потік чернетки:**
- Посилання очищується від `utm`, трекінгу й фрагмента; сайт має бути в `ALLOWED_SOURCES` (`src/rewriting/sources.ts`, точний домен без `www.`). Невідомий сайт або редирект поза списком — помилка до будь-яких запитів.
- Дублі: чернетки в `drafts/` і опубліковані на сайті (`GET /articles`, до 10 сторінок по 40) порівнюються за ключем посилання; `--force` обходить. Глибше за 400 останніх не шукаємо свідомо (власник: та сама історія з іншого видання все одно дозволена, тож додатковий захист, як фільтр за `sourceLink` на сервері, не потрібен: перевірка — зручність, не гарантія).
- Текст: з файлу або `src/fetching` (https, редиректи вручну з перевіркою списку, Readability; дата з метаданих, фото з `og:image`). Невистачає 1000 символів — схоже на paywall, текст вставляють у файл.
- Фото: лише за явним `--image` (`page` — фото зі сторінки), інакше фірмова заглушка `warfare-tech/fallback.png` у Cloudinary (джерело `assets/fallback.svg`, перезаливається `npm run upload-fallback`).
- Рерайт (`src/rewriting`): один виклик, JSON за схемою; українське джерело (більшість літер — кирилиця) спершу переписується українською, а метрика збігів міряється в мові джерела, потім `src/translation` перекладає англійською. Збіги, перевірки (`checks.ts`), `problems` (дзеркало правил сервера) і `warnings` потрапляють у чернетку.
- Чернетка: `drafts/<дата>-<час>-<slug>.md` (поля статті вгорі, нотатки для перегляду під коментарем «not published», збіги з джерелом виділені жирним `**…**`, власник прибирає їх під час редагування, а залишене публікація прибирає сама), поруч `.source.txt` (текст, з якого робився рерайт), для українських джерел ще `.uk.md`.
- Публікація: файл читається, `**` прибираються (лише якщо в чернетці є нотатка `highlights:`, яка каже про `**bold**`; `<mark>` зі старих чернеток — завжди), правила сервера й кирилиця перевіряються, дублі на сайті теж, адмін логіниться, `POST /articles` зі `status: PUBLISHED`, у файл дописуються `publishedAs`/`publishedOn`.

**Рішення, які не видно з коду:**
- Власник сам перевіряє кожну чернетку, тому публікація одразу `PUBLISHED`, а `DRAFT` у базі не використовуємо.
- Фото з чужих видань автоматично не беруться: це питання авторських прав (за рішенням суду ЄС у справі Renckhoff перезавантаження чужого фото на свій сервер потребує дозволу, посилання на джерело його не замінює). Безпечні джерела: DVIDS і af.mil (публічний домен США; перевіряти примітку «IMAGE IS PUBLIC DOMAIN»; за правилами DVIDS новинне використання дозволене, дисклеймер про непідтримку DoW вже в футері сайту (`Footer.tsx`, один раз на всіх сторінках)), Вікісховище, власні фото, фото з дозволом. Якщо фото не з цієї події, у підписі «File photo». Автор головного фото — поле `photoCredit` у чернетці (рядок під `mainPicture`, пишеться лише автор або джерело: «Airbus», «Staff Sgt. … / U.S. Air Force», «Airbus (file photo)»; сайт сам додає «Photo: » і малює підпис на фото в лівому нижньому куті; заповнюється вручну або `--credit="…"` в `npm start` / `attach-image`); без підпису `publish-draft` лише попереджає (власне фото підпису може не потребувати).
- Опис головного фото — поле `photoAlt` у чернетці (рядок під `photoCredit`, необов'язковий, до 200 символів, англійською: перевірка кирилиці його теж ловить); порожнє означає декоративне фото (`alt=''`). Заповнюється вручну або `--alt="…"` в `npm start` / `attach-image` (без реального фото ігнорується). Модель його не пише: вона не бачить картинки. Попередження при публікації для порожнього немає (свідоме рішення: фото часто декоративне).
- Контракт `body` (Markdown): абзаци через порожній рядок; посилання лише http(s); картинка окремим абзацом `![опис](https://res.cloudinary.com/… "підпис з автором")`, опис і підпис обов'язкові, до 10 штук; відео — абзац з одним посиланням на YouTube, текст посилання = підпис (програвач малює фронт: краще `youtube-nocookie.com` і «фасад», щоб не вантажити трекери до кліку; X і Telegram відкладено); HTML заборонений. Модель пише лише звичайні абзаци, картинки, посилання й відео додає власник. Маркер підсвітки збігів — `**` (власник так хоче: `<mark>` у сирому тексті заважав; `<mark>` вже пробували); справжній жирний у статті зберігається, якщо видалити з чернетки рядок `highlights:`.
- Defense One свідомо не в списку: його `robots.txt` забороняє GPTBot.
- Стиль (правила в `src/rewriting/rules.ts`): факти лише з джерела, числа й назви без змін, відносні дати лише абсолютними (потрібна дата публікації), видання називається раз, прямих цитат майже немає (непряма мова), заголовок Title Case (кожне слово з великої, власник так хоче).
- Українські правки: для українського джерела власник правит `<чернетка>.uk.md` (там підсвічені збіги), а `npm run translate` перекладає заголовок, опис і текст з нього й **замінює** ними англійську чернетку (теги, фото, підпис, нотатки лишаються; англійські правки руками губляться, копія — `.pre-translation.md`; у консолі — схожість українського тексту з джерелом). Для англійської чернетки з вписаною українською перекладаються лише абзаци з кирилицею. Публікація відмовляє, поки є кирилиця.

**Граблі:**
- Поруч із чернеткою лежать копії: `.uk.md` (українська версія) і `.pre-translation*.md` (текст до перекладу). Вони схожі на чернетки, і колись `publish-draft` прийняв копію: на сайт пішов старий текст замість перекладеного. Тепер `publish-draft`, `attach-image` і `translate` відмовляють на таких файлах і називають основний `.md`. Опублікований текст без ендпоінта редагування міняється лише в Prisma Studio.
- Схеми для моделі мусять бути м'якими: цей SDK передає в API лише базову форму (`enum` і довжини стають текстом опису), тож строгі правила — у `article.schema.ts`.
- `.gitignore` в `ingestion`: `/drafts/` і `/samples/` з прив'язкою до кореня, бо `drafts/` ховав би й теку з кодом `src/drafts/`.
- Пароль адміна в `server/.env` і `ingestion/.env` має збігатися з тим, що в базі (оновити — `npm run prisma:seed` у `server`; `ADMIN_EMAIL` не міняти, сід шукає за поштою); токен живе 30 днів.
- Фото й чернетки не комітяться (`drafts/`, `photos/`, `samples/`, `.env` у `.gitignore`).

**Відкрите по ingestion:** пакетна обробка списку посилань / RSS; автотестів немає (перевірки поки одноразові скрипти); дата для defence-ua.com лише вручну (на сторінці її немає); пороги збігів і лімітів згадок видання відкалібровані на кількох чернетках.

## Frontend (`client/`)

**Стек:** Next.js **16** (App Router, Turbopack), React 19, TypeScript strict + `noUncheckedIndexedAccess`, SCSS Modules (`sass`), ESLint + Prettier (одинарні лапки, включно з JSX; `eslint-config-prettier/flat`), `next/font` (Manrope, JetBrains Mono через CSS-змінні `--font-manrope`, `--font-jetbrains_mono`).

**Граблі:**
- Next 16 відрізняється від того, що в пам'яті моделі: документація лежить у `client/node_modules/next/dist/docs/` — звірятися з нею (`client/AGENTS.md`).
- `next.config.ts` на Node 22.18+ вантажиться як нативний ESM — немає `__dirname`, тому `process.cwd()`.
- `images.remotePatterns` у формі `new URL(...)` дає `pathname: '/'` і `search: ''` — не пропускає адреси з шляхом і query. Використовувати об'єкт `{ protocol, hostname }`.
- `params` у сторінках — проміс (`await params`); для типів є глобальні `PageProps<'/route'>`, `LayoutProps<'/route'>`.
- `new URL(path, base)` відкидає `/api` з бази — адресу API склеювати рядком.
- `next/image` з `fill` потребує предка з `position: relative` і `sizes`, інакше фото розтягується на весь екран і вантажиться 100vw. Найбільше фото першого екрана — `preload` (у Next 16 замість `priority`).
- `error.tsx` без `'use client'` ламає збірку — 500 віддають усі сторінки, не лише сегмент. У `error.tsx` приходить серіалізована помилка: `instanceof ApiError` там не працює, розрізняти помилки треба на сервері.
- З `page.tsx` / `layout.tsx` можна експортувати лише те, що визначає Next (`default`, `generateMetadata`, `metadata`, конфіг сегмента). Будь-який інший експорт (компонент, функція) ламає `next build`: «"X" is not a valid Page export field». Допоміжні компоненти — в окремі файли.
- `notFound()` і `permanentRedirect()` працюють через спеціальну помилку: викликати в `catch`, не в `try`, і не ковтати всі помилки порожнім `catch`.
- `aspect-ratio` + `overflow: hidden` — блок перестає рости під вміст (стає прокручуваним), текст обрізається. Для обрізання по заокругленню, коли блок має рости, — `overflow: clip`.
- Sass: `5 / 2` у змінній — застаріле ділення з попередженням; пропорції писати як `calc(5 / 2)`.
- Шари з від'ємним `z-index` (фото, градієнт під текстом) — лише всередині батька з `isolation: isolate`, інакше підуть під фон сторінки.
- `align-items: baseline` поруч із flex-елементом, у якого першою стоїть іконка (`svg`), вирівнює по низу іконки: у `svg` немає текстової базової лінії. Там — `center`.
- Проміси, створені заздалегідь і дочікувані кількома `await` підряд: той, що впаде під час першого `await`, дасть unhandled rejection — обробника в нього ще немає. `allSettled` (чи інший обробник) чіпляти одразу, до першого `await`.
- JSX прибирає пробіл, якщо текст і тег (іконка, посилання) стоять на різних рядках — відстань задавати `inline-flex` + `gap` або явним `{' '}`.

**Середовище:** `client/.env.local`: `API_URL=http://localhost:5000/api` — без `NEXT_PUBLIC_`, бо всі запити йдуть із серверних компонентів. Вигляд сторінок можна перевірити справжнім скріншотом, а не лише HTML: `"C:\Program Files\Google\Chrome\Application\chrome.exe" --headless=new --disable-gpu --hide-scrollbars --window-size=1905,700 --virtual-time-budget=30000 --screenshot=<файл.png> http://localhost:3000/news/land` (великий бюджет часу потрібен, бо перший запит до `/_next/image` для великого фото йде до 3 с; на першому знімку фото могло не встигнути). Headless Chrome не робить вікно вужчим за ≈ 500px (`--window-size=390,…` дає ширину 500 і обрізає знімок), тож для телефонних ширин (390, 360, 320) знімок робиться через DevTools-протокол: `Emulation.setDeviceMetricsOverride` із точною шириною (скрипт одноразовий, у репозиторії його немає), висота вікна дорівнює висоті сторінки (інакше lazy-картинки не завантажуються), а в тому ж скрипті перевіряється горизонтальне переповнення (`scrollWidth` проти `clientWidth`; пункти меню, що прокручується, не рахуються). Обкладинки в `public/covers/` стиснуті до 2400px завширшки (sharp, mozjpeg, якість 82, 0.15–0.76 МБ замість 1.4–4.4 МБ), повнорозмірні оригінали лежать у `client/covers-original/` (поза `public`, у `.gitignore`: лише локальна копія, у git їх нема; джерело з DVIDS знайти за автором непросто, тож теку не видаляти). Нове фото обкладинки стискати так само, а розміри в описі обкладинок нижче (4000×…) — це розміри оригіналів.

**Конвенції:**
- Axios не використовуємо: кешування і дедуплікація запитів у Next побудовані на нативному `fetch`.
- Типи дзеркалять JSON сервера: дати — ISO-рядки, необов'язкові колонки — `null`. Параметри запитів — `type`, не `interface` (інакше не присвоюються `Record` у `params`).
- Перерахування — об'єкт `as const` + однойменний тип (як генерує Prisma), не TS `enum`. Тип з ключів мапи — через `keyof typeof` + `satisfies`.
- Дані головної тягне сторінка. Запити й секції підкатегорій — `map` по `HOMEPAGE_SUBCATEGORIES` (ключі `NEWS_SECTIONS`), тож розійтися не можуть; вручну лише featured, Ukraine і Latest. Обидва `allSettled` викликаються до `await` і чекаються разом через `Promise.all`. Помилки — `logIfRejected` з назвою блоку. Секції отримують масив статей пропсом. Порожня секція: Latest і War in Ukraine показують заголовок і `EmptyState` з нейтральним текстом (порожньо і коли запит упав, і коли новин немає); `SubcategorySection` повертає `null`. Посилання на розділ ("View all", "View full coverage") — коли секція не порожня: секція бачить лише показані статті, `total` до неї не доходить. Компоненти не мають зовнішніх відступів — відступи між блоками задає сторінка, через `gap` у flex/grid: секція, що повернула `null`, не лишає зайвого відступу.
- Картки: поки три окремі (Horizontal — фото зліва, мітка, заголовок, автор, час; Compact — фото + заголовок; Vertical — фото, заголовок, опис, час і час читання) з однаковими пропсами `article` + `headingLevel` (за замовчуванням 3). Порівняти і злити (або зібрати зі спільних частин) — пізніше, можлива ще четверта. `ArticleHeadline` — рядок без фото: заголовок-посилання + необов'язковий час (`isShowTime`).
- Посилання в картці — лише на заголовку, `::after` розтягує клік на всю картку; інші посилання — `position: relative` + `z-index`. Декоративне фото поруч із заголовком — `alt=""`.
- Фото в картці: обгортка `card__imageWrapper` (`position: relative`, `aspect-ratio` з токена `$ratio-card` / `$ratio-thumb`, `overflow: hidden`, фон `--color-surface-2`) + `card__image` (`object-fit: cover`). `sizes` — необов'язковий пропс; за замовчуванням — під основне місце картки (розрахунок у коментарі біля `DEFAULT_SIZES`). Hover — підкреслення заголовка кольором акценту. Час — завжди `RelativeTime`; автор + час — `ArticleByline`, не `author && …` в одному компоненті. Час окремо — `$font-mono` `$fs-xs`, у рядку з автором — звичайним шрифтом. Мітка в Horizontal — з `getSectionTagAndLink`, кольоровим текстом капсом (на білому `-text` варіанти проходять).
- Колір розділу — атрибут `data-section="<ключ NEWS_SECTIONS>"` на елементі; глобальне правило в `globals.scss` (цикл `@each`) кладе в нього `--section-color` (текст: `--color-cat-*-text`, Ukraine — `--color-ukraine-blue-text`) і `--section-solid` (фон під білим текстом: `--color-cat-*-solid`, Ukraine — `--color-ukraine-blue`; відрізняються лише в темній темі); `longread`/`news` — `initial`, щоб не успадкувати колір батьківської секції). Модулі лише беруть `var(--section-color, <запасний>)`: мітка картки — колір тексту, мітка hero й фон `PageCover` — тло з `var(--section-solid, …)`, `SubcategorySection` — назва й іконка (16px капсом; іконки — мапа `SECTION_ICONS` у секції, компоненти з `satisfies Record<…>`, розмір 24px через `font-size`). Заголовок підкатегорії — `label` з мапи, капсом через CSS (рішення дизайну).
- Підписи в даних — звичайним регістром ("Air", "War in Ukraine"); великі літери, де треба, — `text-transform: uppercase` у CSS. Капс у розмітці скрінрідер може читати по літерах, як абревіатуру.
- Семантика: один `h1` на сторінку (на головній — у hero), блоки — `section` + `aria-labelledby` з `h2`, картки — `article` з `h3`; `id` заголовків унікальні (в `SubcategorySection` будуються з підкатегорії); однотипні елементи — `ul`/`li`; дата — `time dateTime`.
- Адаптив зроблено (десктоп-першим: база — десктоп, `bp-down` — планшет і телефон). Три рівні: нижче `$bp-lg` (1024px) — планшет, нижче `$bp-md` (768px) — телефон, нижче `$bp-sm` (640px) — одна колонка скрізь. Поля сторінки — CSS-змінна `--gutter` у `globals.scss` (64px, нижче 1024px — `$gutter-md` 32, нижче 768px — `$gutter-sm` 20; її беруть `.container` і `.skip-link`); `.container` — контент до 1400px + поля. Що змінюється: Header — на телефоні логотип і меню у два рядки, меню прокручується вбік без смуги (`NavLink` сам підсуває активний пункт у видиму частину через `scrollLeft` найближчого `nav`, не `scrollIntoView`: той міг би посунути й саму сторінку); Footer — одна колонка на телефоні; Hero — нижче 1024px без пропорції 5:2, `min-height`, на телефоні заголовок `$fs-display-xs` і опис у чотири рядки; сітка підкатегорій 3 → 2 → 1 колонки; War in Ukraine і Top stories на /news — одна колонка нижче 1024px (середні картки Top stories — дві поруч нижче 1024px і до 640px); Latest — одна колонка на телефоні; сітка розділу 3 → 2 → 1; ArticleCardRow — фото зверху нижче 640px (скелет `ArticleRowSkeleton` так само); сторінка статті — одна колонка нижче 1024px (aside під текстом, без прилипання; фото 16:9 на телефоні), картка автора переносить посилання; Pagination — менші кружечки нижче 640px і `flex-wrap`; PageMessage — менші відступи й заголовок, дії переносяться. Заголовки сторінок (`h1` /news, розділу, статті) і скелет заголовка: `$fs-display-lg` → `$fs-display-md` (нижче 1024px) → `$fs-display-xs` (нижче 768px); `PageCover` і `PageCoverSkeleton` — висота `$cover-photo-height` → `-md` → `-sm` (520 / 440 / 380px), на телефоні фото на всю ширину без маски й щільніший градієнт `--gradient-cover-overlay-sm`. `sizes` у всіх картках, Hero, фото статті й `PageCover` розраховані під ці сітки (інакше на телефоні вантажилась би завелика або замала версія фото): змінюєш сітку чи поля — міняй і `sizes`. Модулі стилів — BEM (`block__element`).

**Схема адрес:**
- `/[slug]` — новина (зараз `app/[slug]`); `/news` — усі новини; `/news/[section]` — розділ: `air`, `land`, `naval`, `cyber`, `space`, `uav`, `ukraine` (один шаблон для всіх).
- Лонгріди — **не вирішено і свідомо відкладено** (лонгрідів у базі 0, коли з'являться — невідомо, можливо не цього року): окремі `/longreads/[slug]` (свій layout) або так само `/[slug]`, як новини. Поки діє другий варіант: лонгрід, створений у базі, відкриється за `/[slug]` (aside «Latest in Longreads», крихти ведуть на неіснуючий `/longreads`). Рішення власник прийме сам перед першим лонгрідом (у беклог не заносимо: це його власне нагадування); поки їх нема, зміна адреси нічого не коштує (редиректи не потрібні). Код чекає цього рішення в картках і `ArticleHeadline`: адреса новини там `/${article.slug}`, а `getArticlePath` свідомо не вводимо (лонгріди поки на тому ж роуті, тож вона була б обгорткою без користі; власник: лонгріди зараз не враховуємо). Туду про неї з карток прибрано. Коли лонгріди отримають окремий роут — знайти пошуком `/${article.slug}` і ввести `getArticlePath`. У `app/[slug]/page.tsx` і в `getSectionLabelAndLink` (`article.utils.ts`, де зашитий `href: '/longreads'` для мітки й крихт лонгріда) окремого туду теж нема. Список лонгрідів — `/longreads`. `/authors/[login]` — профіль автора. `/about`, `/advertise`, `/contact`, `/careers` — сторінки футера, поки заглушки на `PageMessage` («<Назва> page is under development», `robots: noindex`, кнопка на головну й посилання на `/news`; кожна в `app/<назва>/page.tsx`, замінюються справжнім вмістом окремо).
- В адресі статті — лише незмінне (slug, тип); підкатегорія може змінитися. Якщо лонгріди отримають окремий роут — сторінки за slug звіряють категорію і редиректять (`permanentRedirect`), якщо стаття з іншого типу. Статичні теки мають пріоритет над кореневим `[slug]`.

Результат у таблиці `next build`: `/` — `○` статична з `Revalidate 5m` (ISR: перший запит після TTL віддає застарілу сторінку, `x-nextjs-cache: STALE`, і в тлі перебудовує її — 9 запитів до API один раз; решта — `HIT` без запитів до API); `/[slug]` — `●` завдяки `generateStaticParams`, що повертає `[]` (перший візит `MISS` і генерація сторінки, далі `HIT`; без неї динамічний маршрут рендерився б на кожен запит; під час збірки до API за статтями не ходимо); `/news` і `/news/[section]` — `ƒ`, динамічні через `searchParams` (HTML не кешується: `cache-control: private, no-store`), але дані кешуються (3 перегляди `/news` = 1 запит до API, кожен `?page=N` — окремий ключ). Частоту перебудови сторінки задає мінімальний TTL серед її запитів (стаття 1000 і aside 300 — сторінка статті раз на 5 хв). Свіжа новина з'являється в списках після ≤ 5 хв і ще одного перегляду (перший перегляд після TTL бачить стару сторінку), а сторінка самої нової статті доступна одразу (генерується при першому візиті); миттєве оновлення — пізніше через `revalidatePath`/`revalidateTag` після публікації. Не додавати на ці сторінки `searchParams`, `cookies()`, `headers()`, `cache: 'no-store'` і `dynamic = 'force-dynamic'`: сторінка стане динамічною, і ISR зникне (після змін дивитись на таблицю збірки: має лишатись `○` або `●`). Відповіді API не 200 не кешуються; невдала регенерація лишає останню добру сторінку; кидок за 9/9 невдалих запитів на головній і ISR узгоджені. `next build` потребує живого API (порядок деплою: спершу API, потім збірка клієнта; з мертвим API збірка падає, і це бажано). П'ять карток з `ArticleByline` (Horizontal, Lead, Side, Row, Grid) уже передають `readingTime={article.readingTime}`, `tsc` чистий. `ArticleCardVertical` теж: рядок `card__meta` з `RelativeTime` і `ReadingTime` моноширинним (шрифт і колір на рядку, діти успадковують), крапка між ними — `.card__time + .card__readingTime::before`, тобто лише коли час публікації відрендерився (на зіпсованій даті `RelativeTime` нічого не малює, і безумовна крапка стояла б першою; так само в `ArticleByline`). `ArticleCardCompact` часу читання не має свідомо: це картка лише з фото й заголовком, без мети (власник).
