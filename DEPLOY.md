# Деплой: порядок дій

Кроки йдуть у порядку виконання: кожен спирається на попередні. Відмічай `[x]`, коли зроблено.

Стан репозиторію (2026-10-15): `tsc` й `eslint` чисті; продакшн-збірка клієнта проходить; сервер у production запускається командою `node dist/src/main`; `.env.example` є в `server/`, `client/` і `ingestion/`; `dotenv` — пряма залежність сервера.

## 1. Рішення (до будь-яких акаунтів)

- [ ] 1.1 Хостинг для трьох частин: клієнт (потрібен Node-сервер: ISR), API (Nest) і PostgreSQL. Приклад простого стеку: клієнт на Vercel (кеш ISR працює без налаштувань), API і база на Railway, Render чи Fly; або один VPS із Docker. **Вибір: клієнт на Vercel, API на Render (Франкфурт), база на Neon (регіон ЄС).**
- [ ] 1.2 Домен. Для першого деплою не обов'язковий (сайт працюватиме на адресі хостингу), але від нього залежать `metadataBase`, canonical і картинка для соцмереж (див. крок 9).
- [ ] 1.3 Що з локальними статтями (зараз 33): перенести дамп таблиць `users` і `articles` чи почати з порожньої бази й опублікувати знову через ingestion. **Вибір: перенести на Neon (кроки 5.4–5.6).**
- [ ] 1.4 Production-гілка — `main`. Хостинг стежить за нею, а `develop` лишається робочою: так недороблений код не потрапляє на прод після кожного `push`.

## 2. Репозиторій

- [ ] 2.1 `git push origin develop` (усе закомічено).
- [ ] 2.2 Перший реліз у `main`. `origin/main` відстає від `develop` і не розійшовся з ним, тож це швидка перемотка: `git checkout main`, `git merge --ff-only develop`, `git push origin main`, потім `git checkout develop`.
- [ ] 2.3 Далі кожен реліз: те саме злиття `develop` у `main`.

## 3. Акаунти й ресурси

- [ ] 3.1 Акаунт(и) хостингу з кроку 1.1.
- [ ] 3.2 Керована PostgreSQL, бажано з автоматичними резервними копіями. Записати `DATABASE_URL` (на керованій базі зазвичай потрібен `?sslmode=require`).
- [ ] 3.3 Cloudinary: той самий акаунт, що й у розробці (фото вже там), нічого міняти не треба.
- [ ] 3.4 Реєстратор домену й DNS (коли буде домен).

## 4. Секрети (ніде не комітити, лише в панелі хостингу)

- [ ] 4.1 `JWT_ACCESS_SECRET`: випадковий рядок від 32 символів, не такий, як у розробці. Згенерувати: `node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"`.
- [ ] 4.2 `ADMIN_EMAIL` і `ADMIN_PASSWORD`: сильний пароль, не як у розробці (`/auth/login` публічний). `ADMIN_EMAIL` потім не міняти: сід шукає адміна за поштою.
- [ ] 4.3 Підготувати значення, які стануть відомі пізніше: `CLIENT_URL` (адреса клієнта, після кроку 6), `API_URL` (адреса API, після кроку 5).

## 5. API і база

- [ ] 5.1 На Render створити Web Service: джерело — GitHub через Git Provider (з «Public Git Repository» автодеплой недоступний), гілка `main`, Region Frankfurt, коренева тека `server/`, мова Node, тип екземпляра Free (спить після 15 хв без запитів, пробуджується до хвилини; платний від 7 $/міс).
- [ ] 5.2 Змінні (зразок — `server/.env.example`): `DATABASE_URL` (**pooled**-рядок Neon), `JWT_ACCESS_SECRET`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `CLIENT_URL` (поки тимчасово, оновити в кроці 6.4). `PORT` і `NODE_ENV` **не задавати**: Render сам дає `PORT` (за замовчуванням 10000, сервер його читає) і ставить `NODE_ENV=production` лише під час роботи; власний `NODE_ENV=production` міг би зупинити встановлення dev-залежностей на збірці. `NODE_VERSION`: 22 (формат перевір у документації Render).
- [ ] 5.3 Build Command: `npm ci --include=dev && npx prisma generate && npm run build` (`--include=dev` потрібен: збірка користується dev-залежностями, а клієнт Prisma не лежить у git). Start Command: `npm run start:prod`. Render за замовчуванням підставляє `yarn`, це треба замінити.
- [ ] 5.4 Міграції створюють схему на Neon. Виконується з твого комп'ютера з **прямим** (не pooled) рядком Neon, бо міграції не дружать із пулером (перевір у документації Neon). У теці `server` (PowerShell): `$env:DATABASE_URL='<прямий рядок Neon>'; npx prisma migrate deploy`. Змінна, задана в оболонці, сильніша за `.env`, тож локальна база не зачіпається. Не `migrate dev`.
- [ ] 5.5 Перенесення статей (крок 1.3), одразу після міграцій і **до** сіду. З локального комп'ютера: `pg_dump --data-only --inserts -t users -t articles "<локальний DATABASE_URL>" > data.sql`, потім `psql "<прямий рядок Neon>" -f data.sql`. Дамп містить хеші паролів і дані: не комітити `data.sql`, видалити після імпорту. Таблицю `_prisma_migrations` не чіпати.
- [ ] 5.6 Сід, теж із прямим рядком: `$env:DATABASE_URL='<прямий рядок Neon>'; $env:ADMIN_EMAIL='<пошта адміна>'; $env:ADMIN_PASSWORD='<сильний пароль>'; npm run prisma:seed`. Сід шукає адміна за поштою й **перезаписує його пароль**, тож `ADMIN_EMAIL` має збігатися з поштою імпортованого адміна (інакше сід спробує створити другого з логіном `admin` і впаде). Так прод-адмін отримує новий пароль, а не локальний.
- [ ] 5.7 Перевірка: `GET <адреса API>/api/articles?limit=1` відповідає 200 і містить імпортовані статті.

## 6. Клієнт

- [ ] 6.1 Створити сервіс клієнта: гілка `main`, коренева тека `client`, Node не нижче 20.9 (краще 22). Не вмикати статичний експорт: ISR потребує Node-сервера.
- [ ] 6.2 Змінна `API_URL` = `<адреса API>/api` (зразок — `client/.env.example`). Має бути доступна і під час збірки, і під час роботи: головна пререндериться під час `next build`, а ISR оновлює сторінки на сервері.
- [ ] 6.3 Збірка: `npm ci && npm run build`, запуск: `npm run start` (на Vercel автоматично). API має бути вже доступним: збірка робить 9 запитів для головної, з мертвим API вона падає (так задумано). Збірці потрібен інтернет: шрифти завантажуються з Google.
- [ ] 6.4 Повернутися в API (крок 5.2) і виставити `CLIENT_URL` = адреса клієнта.

## 7. Перші перевірки після деплою

- [ ] 7.1 Відповідають головна, сторінка статті (потрібна хоча б одна стаття, крок 8), `/news`, `/news/air`, `/about`, неіснуюча адреса дає сторінку 404.
- [ ] 7.2 У відповіді головної й статті після другого запиту є заголовок `x-nextjs-cache: HIT`.
- [ ] 7.3 Фото з Cloudinary показуються (`remotePatterns` уже налаштовані).
- [ ] 7.4 Вхід адміна працює (`POST /api/auth/login`).

## 8. Ingestion → прод

- [ ] 8.1 У `ingestion/.env` поставити `API_BASE_URL` = `<адреса прод-API>/api`, `ADMIN_LOGIN` і `ADMIN_PASSWORD` прод-адміна (ключі Anthropic і Cloudinary лишаються).
- [ ] 8.2 Опублікувати першу статтю: `npm run pub -- 1 --dry-run` (1 — номер чернетки в `ingestion/drafts/`), потім без `--dry-run`.
- [ ] 8.3 Перевірити, що стаття з'явилась: сторінка статті одразу, головна й списки не пізніше ніж за 5 хв.

## 9. Домен і SEO (коли буде домен)

- [ ] 9.1 Підключити домен до клієнта (DNS на хостингу) і оновити `CLIENT_URL` в API.
- [ ] 9.2 Додати `metadataBase` (домен через змінну середовища, наприклад `SITE_URL`) і картинку для соцмереж 1200×630; потім `alternates.canonical` (К5 і К6 з `BACKLOG.md`).
- [ ] 9.3 За бажанням `robots.ts` і `sitemap.ts` (sitemap зі статей API).

## 10. Бажано, але не блокує

- `helmet` і обмеження частоти запитів на `/auth/login`.
- Ендпоінт здоров'я для перевірок хостингу.
- Моніторинг доступності й збір помилок.
- Резервні копії бази (на керованих зазвичай автоматично), перевірити, що відновлення працює.
- Кілька копій клієнта: кеш ISR у кожної свій, тоді потрібен спільний обробник кешу.
- На Linux із glibc оптимізація зображень може потребувати налаштування аллокатора пам'яті для `sharp` (див. `client/node_modules/next/dist/docs/01-app/02-guides/self-hosting.md`).
